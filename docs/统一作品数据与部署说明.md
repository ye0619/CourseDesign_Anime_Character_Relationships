# 统一作品数据与部署

“精选”产品、固定20部收录限制和报告交集已移除。旧/curated地址仅兼容跳转/anime，不再有精选页面或精选API。原有作品、人物、关系、账号关联、用户配置均保留。

## 页面与读取

首页/动画搜索：`/anime`。作品：`/explore/anime/{Bangumi ID}`。全屏角色关系：在详情进入；制作人员和声优均为列表。片单：`/library`。画像与推荐：`/preferences`。

所有Bangumi作品链接进入同一详情页，旧 `/anime/anime%3Abangumi%3A{id}` 自动跳转。页面没有在线/本地切换模块。搜索将同页不同来源按稳定UID合并；不相加两个来源的总数冒充去重总数，按任一来源是否还有分页提供统一上一页/下一页。

读取顺序：用户主动保存的MySQL作品快照→兼容已有Neo4j资料→缺失时访问Bangumi。存在完整本地基础资料时不获取在线作品详情；部分有效字段保留并补全，网络失败回退已有资料。演职员统一接口优先读取已保存分页，其次旧本地名册，再在线补充。真实关系由Neo4j与官方Archive索引按范围查询。

## 保存与更新

详情页的保存/更新无需本地注册。写操作限定本机地址，并要求既有同源CSRF令牌；没有放开管理员维护API。单工作线程、8个排队位置、同作品任务去重、90秒采集预算与分页上限控制资源使用。

SQL先持久化作品、名册及状态，再将作品查询投影、角色、出场和已确认关系幂等写入Neo4j，最后标记COMPLETE/PARTIAL。图写失败仍保留SQL资料；重试可重放。重启把未结束任务标记为PARTIAL。没有跨库ACID保证，不能只见202就认为保存完成。

更新保护manualFields，不重新激活停用记录，不自动删除远端消失的关系/角色；SQL保留上一版previous_payload。分页更新失败保留旧的有效名册。刷新仍可能受来源自身及短时客户端缓存影响，不保证源站修改立即出现。

## 数据库

- Flyway V9新增saved_anime：主键(source,source_id)，payload保存来源标准化基础资料及制作/配音分页；previous_payload保留前一版；status/error_message/updated_at/requested_at表示任务与保存状态。没有修改V1—V8。
- public_credit_snapshot继续用于报告公共名册复用。私人收藏仍在viewer_binding/viewer_collection，不写入公共图谱，令牌不落库。
- Neo4j保留Entity/Character、APPEARS_IN、CHARACTER_RELATION；历史Anime/Person继续兼容。作品摘要是查询投影，已确认剧情边以Neo4j为持久权威，SQL不保存第二套剧情边。
- 新关系附原始类型、来源记录、方向、剧透、结束状态和归档版本。更新不擦除人工字段。旧证据批次的管理员授权范围保持冻结，位于maintenance/legacy-evidence-scope.json；它不参与搜索、作品保存或观看报告。

## API（契约0.19.0）

|路径|能力|
|---|---|
|GET /api/v1/explore/anime|统一搜索入口，兼容旧分页结构|
|GET /api/v1/explore/anime/{id}|统一详情、本地优先|
|GET /api/v1/explore/anime/{id}/credits?kind=STAFF或CAST&page=1|同一人员/配音分页模型|
|GET /api/v1/explore/anime/{id}/graph|统一真实角色图谱|
|GET /api/v1/explore/anime/{id}/saved|保存状态及错误|
|POST /api/v1/explore/anime/{id}/saved?refresh=false或true|保存/更新，202受理，CSRF+本机限制|
|GET /api/v1/session/csrf|获取当前会话CSRF令牌|

原有账号关联、片单、报告和推荐接口保留。viewing-report/3只统计全已看片单，不再有精选交集；旧报告v1/v2仍能读取，过时字段忽略，可重新生成。

## 本机部署与复验

JDK21—25（本机23）、Node24、MySQL/Neo4j沿用锁定版本。首次仅在没有.env时运行Initialize-Local.ps1，然后在frontend执行npm ci；已有.env不要覆盖。

```powershell
.\Start-Project.cmd -JavaHome 'C:\Program Files\Java\jdk-23' -MySqlHome 'D:\Tools\mysql-9.3.0-winx64'
```

默认启动backend工作目录，相对索引位置为../data/index/bangumi；也可设置BANGUMI_ARCHIVE_INDEX为绝对目录。新环境自动执行V9；实际本机V8→V9已成功。MySQL9.3超出当前Flyway官方测试范围，运行时有兼容提示，本机迁移通过不代表所有MySQL9.x组合均获验证。

关系索引使用真实官方ZIP及对应官方元数据散列构建：

```powershell
python scripts/Build-BangumiArchiveIndex.py data/raw/bangumi/archive/dump-2026-10-13.210353Z.zip --sha256 19d12d42502fefeb4a2b14561cc978986a554320b06ca4bbf454d1830b101f90
.\scripts\Test-Project.ps1 -JavaHome 'C:\Program Files\Java\jdk-23'
# 明确运行两库集成（维护夹具按测试自身范围清理）
.\scripts\Test-Project.ps1 -JavaHome 'C:\Program Files\Java\jdk-23' -DatabaseIntegration
# 会实际保存/更新公开作品373267，保留其正常数据
.\scripts\Verify-UnifiedWorks.ps1
```

停止应用用Stop-Project.cmd，两库默认保留。源码回滚依据现状审计中的SHA256快照；V9回退保留新表及数据，仅停用新业务代码。不要删除数据库来回滚界面改动。历史源码快照不是数据库备份。
